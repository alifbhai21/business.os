# Deployment Guide — Phase 13

This document is the operator manual for deploying the Universal Business OS
backend (Render + MongoDB Atlas) and mobile client (Expo EAS). The
scaffolding in this repository is **complete and validated locally**; the
steps that require external accounts/credentials are marked **BLOCKED**
until the operator performs them.

---

## 1. Architecture

```
Expo mobile (EAS build)          Render (Node web service)
┌───────────────────────┐        ┌──────────────────────────┐
│ Android APK / AAB     │──HTTPS▶│ business-os-api           │
│ EXPO_PUBLIC_API_URL   │        │  build: npm ci && tsc     │
└───────────────────────┘        │  start: node dist/index.js│
                                 │  /health  → app liveness  │
                                 │  /ready   → DB readiness  │
                                 └────────────┬──────────────┘
                                              │ mongodb+srv (TLS)
                                              ▼
                                   ┌─────────────────────┐
                                   │ MongoDB Atlas        │
                                   │  staging: business_os_staging
                                   │  prod:    business_os        │
                                   └─────────────────────┘
```

One deployment system is used deliberately: **Render** (blueprint:
`render.yaml` at the repo root). Railway/Vercel are not configured — do not
add a second competing system.

## 2. Backend on Render (blueprint)

`render.yaml` defines two isolated services:

| Service | Plan | Auto-deploy | Database |
|---|---|---|---|
| `business-os-api-staging` | free | on push to main | Atlas `business_os_staging` |
| `business-os-api` | starter | manual promotion | Atlas `business_os` |

Build/start commands per service (`rootDir: server`):

- build: `npm ci && npm run build`
- start: `npm start`
- health check path: `/ready`

Render terminates TLS and forwards the original protocol; the server sets
`trust proxy` and issues **308 redirects** from HTTP to HTTPS in production
(`/health` and `/ready` are exempt so platform probes always succeed).
Graceful shutdown on SIGTERM closes the HTTP listener, then disconnects
MongoDB, then exits (10s force-exit budget) — zero-downtime deploys drain
in-flight requests.

### Operator steps (BLOCKED — requires a Render account)

1. Render Dashboard → **New → Blueprint** → select this repository. Render
   reads `render.yaml` and prompts for every `sync: false` variable.
2. Provide per-environment values (never commit them):
   - `MONGODB_URI` — the **Atlas URI for that specific environment's
     database** (see §3). Staging and production MUST use different
     databases AND different DB users.
   - `CORS_ORIGIN` — explicit comma-separated origin allowlist (the server
     REFUSES production boot with `CORS_ORIGIN=*`).
3. JWT secrets are auto-generated by Render (`generateValue: true`) and are
   unique per service.

### Production boot gate (enforced by code)

With `NODE_ENV=production` the API refuses to start unless:

- `MONGODB_URI` or `DATABASE_URL` is set (no silent in-memory fallback);
- `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are NOT the well-known dev
  defaults and differ from each other;
- `CORS_ORIGIN` is an explicit allowlist (not `*`).

Verified by `server/test/env-security.test.ts`.

## 3. MongoDB Atlas safety

1. **Separate databases**: create `business_os_staging` and `business_os`
   on the cluster. The real-Atlas TEST harness uses ONLY
   `business_os_api_test` (hard-guarded in
   `server/test/atlas/helpers/atlasSafety.ts` — it aborts if connected to
   anything else and performs zero destructive operations).
2. **Restricted database users** (least privilege):
   - `businessos-staging` — readWrite on `business_os_staging` only
   - `businessos-prod` — readWrite on `business_os` only
   - (optionally a separate `businessos-test` for `business_os_api_test`)
   Never reuse the cluster owner account for the app.
3. **Network**: add Render's outbound IPs to the Atlas IP access list
   (Project → Network Access), or `0.0.0.0/0` with the strong credential +
   TLS-only defaults if static egress is unavailable on your Render plan.
4. **Transactions**: the financial engine uses multi-document
   transactions — the Atlas M0+ replica-set clusters support this natively.
5. Credentials live ONLY in gitignored `server/.env` (local) and Render's
   secret store (deployments). Logs print MASKED URIs only.

## 4. CI/CD

`.github/workflows/ci.yml` runs on every push/PR:

```
install → backend typecheck → lint → tests (660) → performance budgets (p95<500ms)
        → npm audit --audit-level=high
        → real-Atlas lane (requires MONGODB_URI repo secret; FAILS LOUDLY if absent)
        → mobile tsc --noEmit
        → secret scan (scripts/security-scan.mjs)
```

`.github/dependabot.yml` watches `/server`, `/mobile` and GitHub Actions
weekly. `npm audit` currently reports **zero high/critical**
(2 moderate: exceljs→uuid, no fix without an exceljs downgrade).

### Operator step (BLOCKED)

Add repository secret `Settings → Secrets and variables → Actions →
MONGODB_URI = <Atlas test-cluster URI>`. The atlas job intentionally fails
with a clear error while this secret is missing — it never silently skips.

## 5. Mobile via Expo EAS

Configuration added in Phase 13:

- `mobile/eas.json` — profiles: `development`, `preview` (**APK**, internal
  distribution / sideloading for pilot), `production` (AAB for Play Store).
- `mobile/app.json` — `android.package` /
  `ios.bundleIdentifier`: `com.universalbusinessos.mobile`.
- API base URL comes from `EXPO_PUBLIC_API_URL` (read by `mobile/src/api.ts`).

### Operator steps (BLOCKED — requires an Expo account)

1. `cd mobile && npx eas login && npx eas init` (writes `extra.eas.projectId`).
2. Set the API base URL per profile — edit the `EXPO_PUBLIC_API_URL` env
   values in `eas.json` (currently empty strings so a forgotten value fails
   loudly instead of pointing builds at localhost):
   - preview/staging → the Render staging URL
   - production → the Render production URL
3. Build: `npx eas build -p android --profile preview` (APK) /
   `--profile production` (AAB). First Android build generates the keystore
   via EAS (credentials stay in EAS servers, never in git).
4. Play Store: create the developer account, upload the AAB
   (`eas submit`). Sideloading the APK is sufficient for the pilot.

## 6. Environment variables reference (server)

| Variable | Required in production | Notes |
|---|---|---|
| `NODE_ENV` | yes (`production`) | gates HTTPS redirect + boot validation |
| `PORT` | provided by Render | default 4000 locally |
| `MONGODB_URI` | yes | Atlas URI incl. db name; masked in logs |
| `JWT_ACCESS_SECRET` | yes | ≥16 chars, ≠ dev default, ≠ refresh secret |
| `JWT_REFRESH_SECRET` | yes | ≥16 chars, ≠ dev default |
| `JWT_ACCESS_EXPIRES_IN` | no | default `15m` |
| `JWT_REFRESH_EXPIRES_IN` | no | default `30d` |
| `AUTH_MAX_LOGIN_ATTEMPTS` / `AUTH_LOCKOUT_MINUTES` | no | default 5 / 15 |
| `RATE_LIMIT_MAX` | no | default 100 req/min |
| `CORS_ORIGIN` | yes | explicit allowlist; `*` rejected |

## 7. Health & readiness

- `GET /health` — process liveness (always 200 when running).
- `GET /ready` — 200 only when `mongoose.connection.readyState === 1`;
  503 `not_ready` otherwise (never falsely reports connected). Both paths
  bypass the rate limiter and HTTPS redirect.

## 8. Known limitations / blocked items

- **BLOCKED — actual staging/production deploys**: need a Render account +
  Atlas network/user setup (§2, §3). Blueprint and docs are ready.
- **BLOCKED — CI atlas lane green run**: needs the `MONGODB_URI` repo
  secret; workflow fails clearly until then.
- **BLOCKED — EAS builds / Play Store**: need an Expo account and the
  real `EXPO_PUBLIC_API_URL` per environment (§5).
- **DEFERRED — exceljs moderate advisories** (via uuid): upstream fix would
  require an exceljs major downgrade; revisit when exceljs updates.
